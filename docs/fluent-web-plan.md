# Chat · Fluent web design reset

This replaces the previous visual-polish checklist. Use [Microsoft Fluent 2 for Web](https://fluent2.microsoft.design/components/web/react/) as the reference for controls, hierarchy and states. Fluid Framework is a collaboration runtime and is outside this task. Implement the visual rules in the existing HTML/CSS. No new framework, web font, CDN or icon library is needed.

## Review findings and implementation order

Work from `/workspace/projects/ms-durable`. Complete each step before starting the next. Keep existing element IDs, form semantics, event handlers, HTTP routes, approval payloads and SSE reconciliation. Use synthetic data for screenshots.

1. **Establish the comparison.** Read `static/index.html`, `tests/ui.ts`, and `evidence/ui-{desktop-dark,mobile-light}.png`. Trace one turn from prompt → tool details → approval → response. The old view outlines the activity, request, filename, message and composer; three of those edges compete for attention. Acceptance: identify `.activity`, `.approval` and `#notice` separately; the sidebar divider and keyboard focus rings serve different purposes and stay.
2. **Set the type and colour scale.** Edit the existing `:root` rules in the inline stylesheet. Use Segoe UI with system fallbacks, 14px/20px body text, 12px supporting text, sentence-case headings and semibold titles. Use neutral canvas, navigation, hover and selected surfaces in both colour schemes. Reserve brand blue for primary commands, links and focus. Use a 4px control radius and an 8px dialog radius. Acceptance: switching OS theme keeps the same layout; neutral secondary text is readable in both.
3. **Flatten navigation and transcript.** In `#sessions`, identify the selected row by a neutral fill and semibold title; keep `aria-current`. In `newTurn`, put a visible “You” label and the prompt on the reading axis. Remove the speech bubble, inline-code outlines, animated ellipsis and decorative lines around compaction. Keep tool details collapsible with a disclosure marker. Acceptance: at 1280px prompts, replies, activity and composer share a reading column; command output and long paths remain accessible.
4. **Simplify decisions.** In `renderApprovals`, use one heading announcing the permission request, the actual operation and subject, optional intention, disclosure and two text buttons. Remove the left stripe, nested filename box and decorative button icons. Keep “Deny” and “Approve once” equally legible. Never hide the command or change what either button does. Give `#notice` a neutral message-bar surface, icon, text and dismiss control; remove its stripe. Acceptance: neither surface depends on colour to communicate its meaning.
5. **Treat the composer as an input.** Use a single neutral field outline with visible keyboard focus. Disable Send when the draft is empty or whitespace-only. Keep Send/Queue message, Stop, model selection, Shift+Enter and IME handling. Verify that typing and clearing update the disabled state immediately, and that stopping an active turn remains possible with an empty draft.
6. **Check small screens and system settings.** Keep the mobile drawer, 44px touch targets and native dialogs. Test an open approval at 390×780; check that the decision buttons and composer are inside the viewport. Test focus by keyboard. In forced colours use system highlight for the selected session and preserve focus outlines. No gradients, accent rails, pill badges, avatars or decorative shadows on ordinary content.
7. **Verify and record.** Run `make test-ui` for Chromium fixture tests, then `make check`. Confirm the fixture still posts approval and compaction requests. Inspect the new light/dark screenshots from the test's reported `evidence` directory before copying representative images to `evidence/`. If a test fails, fix the component; do not lower an existing assertion to pass. Use `make test-browser` only for an explicitly authorised live Copilot run; it consumes model allowance. Record commands actually run and any untested states. Do not deploy as part of this pass.
